# Eval-Methodology Audit & Hardening — Design Spec

> **For agentic workers:** This is the design/spec. The implementation plan lives at
> `docs/superpowers/plans/2026-07-02-eval-methodology-hardening.md` (written after this spec is approved).
> This pass produces **documents only** — no feature code. When the plan is executed, it touches
> **evaluation tooling only**, never harness behavior (see Non-Goals).

**Goal:** Close five evaluation-methodology gaps in Labmate's harness A/B and routing evals so a
reported number means what it claims — task success (not a proxy), measured with variance (not a
single green run), under a controlled single-axis comparison (not a mixed-conditions baseline),
on data not generated by the model under test (no leakage), against a trivial baseline (so a delta
is interpretable).

**Motivation:** A review of an external KBQA paper surfaced five evaluation traps: (1) reporting a
proxy as the goal, (2) claiming a win from single-run marginal ablations with no variance,
(3) comparing against baselines captured under different conditions, (4) eval data drawn from the
same distribution/model as the thing under test, (5) tiny curated sets with no long-tail and no
trivial baseline. This audit checks whether Labmate's own evals repeat them and scopes the fixes.

**What we already do right (do not regress):** cross-family judge to avoid self-grading bias;
`TRIALS=N` pass-rate scoring because c1/c3 flake on the Q4 model; a locked hand-written routing
`seed` slice; `skill_first`-vs-`react` is a properly controlled single-axis comparison.

## Part A — Methodology Audit (findings)

All findings are grounded in reads of `eval/run_routing_eval.py`, `eval/extend_eval.py`,
`eval/seq_ab/{run_mode.sh,run_seq_ab.py,results-*.json}`, `eval/reports/*.md`,
`eval/pregate_recall_eval.py`, and the orchestrator flag sites. File:line references are
approximate (subject to drift) but were verified at audit time (2026-07-02, HEAD `f054ba6`).

### A1 — Proxy vs Goal

| Metric we gate on | What it actually measures | Real goal | Gap / risk |
|---|---|---|---|
| **Routing accuracy ≥ 0.80** (`run_routing_eval.py`) | Correct **skill selection** — top-1, majority vote over `--repeats` (default **1**), reports a stability ratio but **no stddev/CI** | Task actually **completed** | Proxy. Correct routing → failed task still scores "correct." Threshold is a **CLAUDE.md policy, not code-enforced** — `run_routing_eval.py:~426` only prints `<-- LOW` when a skill < 0.8. |
| **seq_ab `ok` / "completion"** (`run_seq_ab.py`) | The harness's **own** `reconcile_ok()` verdict — self-reported | Task completed | The system under test grades itself. `reconcile_ok` does downgrade unverified "I fixed it" claims (genuinely good), but completion remains self-scored, not independently verified. |
| **seq_ab "honesty"** | A **manual, offline** cross-family (Claude) read of `final_answer` vs `ok` | No unearned success claims | The right instinct (cross-family) but **not systematized** — not reproducible, not recorded in the results file, not gated. |

**Where routing accuracy stands in for task success:** the entire skill-acceptance gate (new skill
≥ 0.80, no existing skill drops > 0.05) treats *routing correctness* as the acceptance signal for
*"the skill works."* Nothing downstream checks the routed skill then completes the task.

**(b)** single-run/anecdotal/bundle-measured · **(c)** no measurement (intuition/derived) ·
**(d)** explicitly off/opt-in, no benefit claim.

| `ROUTE_EDIT_TO_REACT` | `1` | **a** | Load-bearing prod change; A/B showed default-1 killed fabricated completion (compound 0/3→2/3). |

**OFF / opt-in (no prod behavior, no measured benefit):** `ENABLE_CONDITIONAL_GATES`,
`ENABLE_MESSAGE_REPAIR`, `ENABLE_FINALIZE_REVISION`, `ENABLE_SKILL_CURATOR`,
`ENABLE_LOOP_CHECKPOINT`, `CRITIQUE_ARTIFACT_TYPES` (auto-critique), `ENABLE_ROUTING_PREGATE`.
Two (`ENABLE_LOOP_CHECKPOINT`, the pregate) carry comments that literally say "turn on after the
A/B validates it" — an A/B that never ran.

**Headline:** of ~15 quality-affecting flags, **exactly one decision path** rests on multi-trial
data. Numeric defaults (`12`, `4`, `16000`, `600`, `5`, `2`) are intuition. OFF-by-default is used
as a substitute for measurement. The one genuinely-measured threshold (`0.58`) is inert.

**Retirement candidates (no measured benefit):** the six OFF/opt-in features above are dead-but-
wired. Retiring them is *code cleanup*, out of scope for this measure-first pass, but they are
flagged here so a later decision can either measure-then-keep or remove them. This spec does **not**
retire any flag.

### A3 — Uncontrolled comparisons (more than one axis moved)

1. **Current 12B code vs committed `results-skill_first.json` (31B).** The committed baseline was
   captured on **Gemma 4 31B** (commit `c2508f9`, 2026-06-27); HEAD is now **12B** (`f054ba6`,
   2026-07-02). Any "current vs committed" read moves **model + code** at once. *This is the one to fix.*
2. **`results-skill_first.ref.json` (pre-agentic-fix) vs `results-skill_first.json` (post-fix).**
   Moves a whole **bundle of code changes** — valid as a "fabrication fixed" narrative, invalid as a
   controlled single-axis test.
3. **Routing cases generated on 31B, evaluated on whatever model is up (now 12B).** Generation and
   evaluation models can differ and both drifted since capture.
4. **`ROUTE_MAX_TOKENS` latency memory (37s→19s)** captured before the 12B swap; model axis moved.

**Properly controlled (the template to copy):** `skill_first` vs `react` — paired capture (same
commit, same model, same fixtures reset per trial, only `SEQUENCING_MODE` varied).

### A4 — Leakage

`extend_eval.py` generates routing cases by prompting **gemma-4-31b** (default `--model`) with the
**same SKILL.md description text** the router later sees in its catalog prompt. Risk: generated
phrasings echo the description wording → routing accuracy is inflated relative to real,
differently-worded user requests. The generation prompts explicitly show the model the skill name +
description and ask for "diverse, realistic user task phrasings."

**Partial mitigation already present:** the 77-case hand-written `seed` slice
(`routing_eval.seed.jsonl`, `source="seed"`, locked, **not** model-generated). But it is **mixed
into the working set**, **never reported as its own number**, and still **routed/graded by the same
model family** — so it can't currently quantify inflation.

**Inflation is measurable:** accuracy on model-generated cases minus accuracy on a truly held-out,
non-model-generated slice = an estimate of the leakage inflation. We don't compute it today.

### A5 — Coverage + trivial baseline

- **seq_ab:** 5 fixed cases (c1/c2/c3 compound, c4/c5 control). No rare/hard/long-tail. c1/c3 flaky.
- **Routing:** 2–9 cases/skill (uneven), 6 negative "should-decline" cases, some boundary
  disambiguation cases. No explicit long-tail/rare-skill handling.
- **No trivial or majority baseline anywhere.** A "0.80" or a "2/3 pass" is reported with no
  reference point, so the reader can't tell if it beats always-guess-the-majority-skill or
  always-`skill_first`. c4/c5 are sanity controls, not null-hypothesis baselines.

## Part B — Design decisions (locked with the user, 2026-07-02)

1. **Held-out anti-leakage slice:** **Claude drafts, user curates.** Claude (cross-family) authors
   ~30–40 held-out routing cases; user reviews/prunes before locking. Kept separate from `seed` and
   working sets; reported as its own accuracy number.
2. **Trivial baselines:** **Both.** Routing gets a majority-class + random baseline; seq_ab gets an
   always-`skill_first` / no-op-finish reference reported beside each compound delta.
3. **Variance bar:** **Wilson 95% CI on pass_rate + a written policy.** Require `TRIALS ≥ 3`; no
   flag default is called a "win" without a committed results file whose delta has non-overlapping
   (or explicitly-argued) intervals vs baseline. Enforced by a check in the results emitter, **not**
   a CI gate.
4. **Re-baseline scope:** **Protocol + re-capture the baseline on 12B.** Define the frozen-axis
   protocol + a provenance header, and re-capture only the `skill_first`/`react` baseline under the
   current 12B + HEAD. Per-flag sweeps of the class-(c) numeric defaults become prioritized backlog.

## Part C — Design of the fixes (five workstreams)

Each workstream is eval-tooling only. Boundaries are drawn so a reviewer could accept one and reject
its neighbor.

### WS1 — Proxy-vs-goal labeling (scope item 1)
**Produces:** every gated metric in `run_routing_eval.py` and `run_seq_ab.py` reports/output is
explicitly labeled as **proxy** or **goal**, with a one-line "what this does NOT measure" caveat.
No metric changes — only honest labeling in the printed report + the report `.md` templates.
**Interface:** a `METRIC_MEANING` block at the top of each report (routing = "skill selection, not
task completion"; seq_ab `ok` = "harness self-reported completion, not independently judged").
**Acceptance:** a reader of any report can, without external context, see which numbers are proxies.

### WS2 — Variance bar + one-flag A/B (scope item 2)
**Produces:** (a) a Wilson-95%-CI helper computed over the per-case trials in `run_seq_ab.py`
aggregation (adds `pass_rate_ci_low`/`pass_rate_ci_high` next to the existing `pass_rate`); (b) a
thin **single-flag A/B** entry point that runs the fixed case set twice — flag default vs the one
alternative value — freezing everything else, and prints the paired pass-rate delta **with CIs and
the trivial baseline** (WS5); (c) a written **variance policy** doc: `TRIALS ≥ 3`, non-overlapping
(or argued) CIs, committed results file, before any default is claimed a win.
**Interface:** `run_seq_ab.py` gains `--flag NAME --values A,B` (or an env-driven equivalent);
emitter refuses to stamp `"win": true` without the CI condition met.
**Constraint:** this varies **flags that already exist** — it introduces **no new harness flag or
mechanism**. It only *measures* existing ones.
**Acceptance:** running the one-flag A/B on `ROUTE_EDIT_TO_REACT` reproduces the known win with
non-overlapping CIs; running it on an unmeasured class-(c) flag prints "no measured benefit."

### WS3 — Frozen-axis protocol + provenance + re-baseline (scope item 3)
**Produces:** (a) a **provenance header** written into every results JSON — `model` (gguf basename),
`git_sha`, `captured_at` (passed in, not `Date.now()`), and the full env-flag snapshot; (b) a
**protocol doc** stating the rule "freeze model + code + fixtures, vary exactly one axis per
comparison," with the current uncontrolled comparisons (A3) listed as what not to do; (c) a
**re-captured `skill_first`/`react` baseline on 12B under HEAD**, replacing the stale 31B files
(the old ones move to `*.31b.ref.json` for history).
**Interface:** `run_seq_ab.py` stamps the header from env + args; a tiny validator warns when two
results files being compared disagree on `model` or `git_sha`.
**Acceptance:** the two committed baseline files carry a 12B provenance header; the validator flags
the stale 31B `.ref` if someone compares against it.

### WS4 — Cross-family held-out anti-leakage slice (scope item 4)
**Produces:** `eval/routing_eval.heldout.jsonl` — ~30–40 hand-curated, **not** Gemma/Qwen-generated
cases (Claude-drafted, user-curated), kept **separate** from seed + working sets, never fed to
`extend_eval.py`. `run_routing_eval.py` gains a `--heldout` slice that reports its accuracy
**separately** and prints the **inflation estimate** = `generated_acc − heldout_acc`.
**Interface:** a distinct `source="heldout"` tag; the runner never mixes it into the working-set
accuracy.
**Acceptance:** the report shows three numbers — generated-set acc, held-out acc, and their gap —
so leakage inflation is quantified rather than assumed.

### WS5 — Long-tail coverage + trivial baselines (scope item 5)
**Produces:** (a) additional **rare/hard/long-tail** cases — rare-skill positives, harder boundary
disambiguations, more negatives — added to the working set (routing) and 2–3 harder compound cases
to seq_ab; (b) a **trivial baseline** printed next to every delta: routing = majority-class +
random accuracy over the same case set; seq_ab = always-`skill_first` / no-op-finish pass-rate.
**Interface:** baselines computed from the same case set at report time (no model calls for the
majority/random routing baseline; the seq_ab no-op baseline is a recorded reference run).
**Acceptance:** every reported delta sits next to its trivial baseline; a delta below the trivial
baseline is visibly not a win.

## Part D — Non-goals & constraints

- **Measure first.** No new retry/guard/harness mechanism. Goal-level retry already exists
  (`MAX_GOAL_ATTEMPTS`) — do **not** add another. All work here is *how we evaluate*, not new
  harness behavior.
- **No harness-behavior code.** The plan touches `eval/` tooling, report templates, and docs only.
  It does not modify `services/orchestrator/` behavior. (Re-capturing baselines *runs* the harness
  but does not change it.)
- **This pass = documents only.** Deliverables are this spec + the implementation plan. No feature
  code until the plan is approved.
- **Cross-family grading.** Any result-file judgement uses a cross-family model (Claude — not
  Gemma/Qwen), consistent with existing practice. WS1/WS2 make that judgement reproducible; they do
  not replace it with self-grading.
- **Don't touch `routing_eval.seed.jsonl`** (locked) or introduce leakage into the held-out slice.

## Part E — Backlog (explicitly deferred, prioritized)

1. **Per-flag variance sweeps** for the class-(c) numeric defaults, highest-impact first:
   `MAX_GOAL_ATTEMPTS` (CLAUDE.md already flags it), `LABMATE_TOOL_RESULT_BUDGET`,
   `LOOP_REPEAT_LIMIT_MUTATING`, the two breakers (`GOAL_DEADLINE_S`, `NOPROGRESS_LIMIT`). Use the
   WS2 one-flag A/B once it exists.
2. **Isolation A/B** for `LABMATE_REFUND_REPEAT_LOAD_SKILL` (the `"0"` path built for exactly this).
3. **Measure-then-decide** on the six OFF/opt-in retirement candidates (A2): either a WS2 A/B shows
   a benefit and they turn on, or they're retired as dead code.
4. **Systematize the honesty judge** — turn the manual cross-family read into a recorded, rerunnable
   judgement pass over the results files.
5. **Enable `ENABLE_ROUTING_PREGATE`** if/when its measured `0.58` threshold is confirmed under 12B
   (its win is currently inert).
